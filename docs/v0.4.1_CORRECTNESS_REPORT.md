# v0.4.1 correctness report

| Дефект | Причина | Исправление | Regression test |
| --- | --- | --- | --- |
| Резерв учитывался дважды | Он добавлялся в `entityIds` и `reserveIds` | После ввода добавляется только в side participant array | 1 |
| Поддержка усиливала чужую сторону | Общий `supportIds` | Attacker/defender support arrays и side filtering | 2, 3 |
| Unit занимал две роли | Роли не были взаимоисключающими | Role invariants после каждой команды | 4 |
| Боеприпасы списывались у заявленной поддержки | Не было eligibility/usage | Списание после фактического включения | 5, 6, 7 |
| Heavy AT учитывался неверной стороне | Penetration видел общий список | Используются attacker participants + attacker support | 8, 9 |
| Фантомный meeting | Сравнивался следующий route hex до проверки | Conflict detection получает только validated intents | 10–16 |
| Групповой приказ телепортировал части | Origin брался у leading unit | Colocation validation и транзакционный шаг | 17–20 |
| Reserve triggers игнорировались | Executor выбирал любой friendly contact | Реальные triggers, правильный rank и expiration | 21–25 |
| HQ блокировал advance | Захват выполнялся после проверки гекса | HQ разрешается до повторной occupancy check | 26–29 |
| Два порога потерь | `lossTolerance` и reaction работали вместе | Только `LOSS_TOLERANCE_STEPS`; legacy reaction мигрируется | 30–33 |
| Временные CP исчезали | Planning сбрасывал CP в base max | `effectiveMaxCommandPoints` учитывает срок эффекта | 34–38 |
| AAR смешивал новые и старые потери | Использовался текущий состав | Event segment + отдельный understrength list | 39–43 |
| Replay мог зависеть от порядка данных | Не было end-to-end проверки | Stable sorting, idempotency и acceptance replay | 44–46 |
| Legacy reaction оставалась активным типом | Persistence и domain использовали один union | Отдельный legacy input; active union не содержит `loss_threshold` | 47–51 |
| Reserve contract обещал будущие triggers | Type union был шире executor | Active union содержит только два правила; migration очищает legacy | 52–55 |
| Последний импульс был задан числом `5` | Engine и UI дублировали конфигурацию | `EXECUTION_IMPULSES`, count, last и night helper | 56–58, 71 |
| Fallback мог быть технически некорректным | Не было полной повторной проверки | Полная validation до мутации и при trigger | 59–64, 74 |
| Не было reactions/persistence acceptance | Один flow концентрировался на movement/combat | Два детерминированных full acceptance flows | 71–80 |
| Инварианты не проверяли все роли и usage refs | Проверялись только отдельные пересечения | Side, role, support usage и active-condition invariants | 81–85 |
| Не были закрыты CP/AAR границы | Не хватало stacking/no-combat checks | CP stacking/floor/clone и event-index boundaries | 87–91 |
